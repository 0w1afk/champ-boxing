# Процесс создания сайта

Процесс ведёт основная сессия OpenCode, специализированные роли — субагенты проекта, изображения генерирует и обрабатывает ChatGPT. Реализация — последний шаг. Каждый этап заканчивается гейтом: следующий не начинается без явного утверждения пользователя.

Команды: `/pipeline status`, `/pipeline next`, `/pipeline approve G3`, `/pipeline rework G5 что изменить`. Без команды то же самое делает скрипт напрямую: `node .agents/skills/pipeline/scripts/gate.mjs …`.

## Как проверяются переходы

Переходы проверяет скрипт `.agents/skills/pipeline/scripts/gate.mjs`, а не модель.

| Файл | Назначение |
|---|---|
| `docs/process/gates.json` | правила: порядок, зависимости, обязательные материалы, чек-листы |
| `docs/process/status.json` | состояние, пишет только скрипт |
| `docs/process/status.md` | сводка для чтения, генерируется скриптом. Текущий этап вычисляется, а не задаётся вручную |

Жизненный цикл гейта:

```text
не начато или устарело → start → в работе → submit → на утверждении → approve → утверждено
                                                  ↑                                 |
                                        на доработке ←────────── rework ─────────────┘
```

| Переход | Скрипт проверяет |
|---|---|
| `start` | статус «не начато» или «устарело»; вся цепочка предыдущих гейтов утверждена; для G1 закрыт чек-лист S0 |
| `submit` | статус «в работе» или «на доработке»; вся цепочка утверждена; обязательные файлы существуют и не пусты; для G9 закрыт чек-лист запуска |
| `approve` | статус «на утверждении»; те же проверки заново, на случай если файл пропал; передана дословная фраза пользователя |
| `rework` | указана причина; статус «утверждено», «на утверждении» или «на доработке» |

Снятие выполненного пункта чек-листа через `item ... --undo` автоматически переводит связанный гейт и уже начатые зависимые гейты в `устарело`. Даты статусов и истории вычисляются в таймзоне `Europe/Moscow`.

Отдельно проверяется, что G7 требует все `G6.*` и G6, G9 требует все `G8.*`, а пустой список экранов проверку не проходит.

Скрипт исключает случайные ошибки перехода. Подлинность слов пользователя он проверить не может, а `status.json` можно изменить вручную. Такие правки запрещены и видны в истории git.

Тесты: `node --test ".agents/skills/pipeline/scripts/gate.test.mjs"`.

Правка G4 не затрагивает G5: цвета и основа не зависят от текста. Но пока G4 на доработке, следующие гейты утвердить нельзя, потому что он входит в их цепочку. Неначатые гейты остаются неначатыми. При устаревании G9 чек-лист запуска сбрасывается.

Состав экранов меняется только между утверждением G2 и утверждением G4. Позже новая страница оформляется через `rework G2`.

## Что считается кодом сайта

Код сайта не пишется до утверждения G7. Исключение — прототипы:

- `docs/design/drafts/` — одноразовые HTML + Tailwind прототипы S5–S6 без логики. Это дизайн-артефакт и после явного утверждения — источник правды для реализации. В код продукта прототип не копируется механически: сборка идёт по токенам, спецификациям и текстам; разметка прототипа — образец композиции, а не готовый код.

`package.json` до S7 остаётся заготовкой без рабочей конфигурации. Стек, зависимости и скрипты определяются на S7 и фиксируются в `docs/design/handoff.md`.

## Роли и модели

| Роль | Кто | Зачем |
|---|---|---|
| Оркестратор | основная сессия OpenCode | диалог, интервью, концепция, гейты, механические проверки, приёмка |
| Маркетолог | субагент `marketer` | исследование, стратегия, структура |
| Копирайтер | субагент `copywriter` | тексты всех экранов |
| UI/UX-дизайнер | субагент `designer` | HTML + Tailwind прототипы, токены, спецификации, задания на изображения |
| Frontend-разработчик | субагент `frontend` | Astro-код по утверждённому прототипу |
| Дизайн-ревьюер | субагент `reviewer` | независимая визуальная и UX-проверка в отдельном запуске |
| Изображения | `image.mjs` | генерация и обработка через ChatGPT (Codex) |

Роли лежат в `.opencode/agent/` и запускаются как субагенты; модель наследуется от основной сессии. Ревьюер и автор работают на одной модели: независимость держится на отдельном запуске без контекста автора и на требовании доказательств к каждой находке.

Рутинный помощник на внешней модели (DeepSeek) удалён: механические проверки выполняет оркестратор и фиксирует факты в `qa.md`, оценку делает `reviewer`.

Дефект, оставшийся после двух кругов исправлений, оркестратор исправляет сам по правилам `.opencode/agent/frontend.md`, а проверку снова выполняет `reviewer`.

### Изображения через ChatGPT

`image.mjs` запускает Codex из приложения ChatGPT на дешёвой модели во временной папке вне проекта, поэтому Codex не читает правила и файлы репозитория. Файл и JSON с промптом сохраняются в `docs/design/generated/`, существующие файлы не перезаписываются. Генерация расходует лимит подписки ChatGPT, поэтому промпт готовится заранее, а результат сначала показывается пользователю.

Политика изображений:

- реальные фото клуба и тренеров из `old_site_files/` обрабатываются под студийную съёмку (референс в `--ref`);
- генеративные люди — только иллюстративные сцены; они не выдаются за конкретных тренеров, клиентов и посетителей клуба;
- сгенерированные в `workspace-784888f5-982a-47ad-b35d-9e5f9d2e4958` образы тренеров и клиентов не используются.

Figma в процессе не участвует: чтения и записи через MCP убраны, источники правды — прототипы и файлы в `docs/design/`. Прежние записи о Figma в истории S0 сохраняются как история.

### Цикл S8 на один экран

1. `frontend` собирает экран в Astro, собирает проект и снимает скриншоты 1440 и 390.
2. Оркестратор запускает механические проверки: сборка, линтер, консоль браузера, битые ссылки и якоря, `prefers-reduced-motion`; факты из вывода пишет в `docs/review/<экран>/qa.md`.
3. `reviewer` сравнивает экран с утверждённым прототипом и скриншотами, возвращает вердикт с доказательствами.
4. `frontend` исправляет находки. Не больше двух кругов, остаток выносится пользователю.
5. Оркестратор выполняет `submit`, пользователь утверждает экран, затем начинается следующий.

### Чек-лист запуска на S9

Качество интерфейса проверяют механические проверки оркестратора и `reviewer`. Кроме него, перед G9 должны быть закрыты пункты чек-листа `s9`: страницы ошибок, `robots.txt`, `sitemap.xml`, Open Graph, ссылки записи (WhatsApp и телефон), аналитика, согласия, политика конфиденциальности, домен и HTTPS, поведение при отказе встраиваемых сервисов.

Каждый пункт закрывается с доказательством через `gate item s9 <пункт> --note "..."`. Неприменимый пункт закрывается через `--na "причина"`. Проверки, зависящие от боевого домена, выполняются на нём, а не на локальной сборке. Юридические формулировки подтверждает ответственный человек, а не агент.

## Переход на OpenCode

Настройку заново проверяет чек-лист `opencode` в `status.md`. Пока он не закрыт, скрипт не примет `submit G5`. Уже утверждённые G1–G4 не затрагиваются: сменились исполнители, а не материалы.

1. `command`: команда `/pipeline` доступна в OpenCode и управляет статусом через скрипт.
2. `agents`: пять ролей из `.opencode/agent/` запускаются как субагенты и отвечают на простое задание.
3. `images`: `image.mjs` создаёт тестовое изображение через ChatGPT.

Каждый пункт закрывается через `gate item opencode <пункт> --note "что проверено и результат"`.

Здесь `gate` означает `node .agents/skills/pipeline/scripts/gate.mjs`.
